# 路线图 —— 从「宅盘系统」到「一生轨迹推演与对轨校准」

> 本文是设计决策记录，不是愿望清单。凡与 [README](../README.md) 的「设计上的几条硬规则」
> 冲突之处，均在本文 **§8** 明确列出修订与理由，不做静默变更。

---

## 1. 定位的变化

原定位：**给一处房产做三派合参**，输入是房子，成员八字是修饰项。

新定位：**给一个人推演一生轨迹，并用他的真实经历反过来收敛取象范围**。
输入是人，房子变成他人生中的一段段环境。顺序是古法的「一命、二运、三风水」：

| 序 | 层 | 承担什么 | 数据来源 |
|---|---|---|---|
| 一 | 命 | 先验：一生的底盘与分段 | 八字四柱＋大运、紫微十二宫＋大限四化 |
| 二 | 运 | 触发：某一年、某一刻发生什么 | 流年流月、时家奇门占局 |
| 三 | 风水 | 调节：同命不同运的那部分差异 | 玄空飞星、八宅、山向奇门 ＋ 居住史 |

概率上的对应关系：

```
P(事件) = 先验(命) × 调节(风水) × 触发(运)
                ↓
          个人化校准层        ← 唯一会被用户数据改动的地方
```

**古法权重、飞星取象、十神定义一律不参与学习。** 学习只发生在校准层，见 §7。

## 2. 为什么以本仓库为宿主（决策记录）

候选方案有三：扩展八紫（Flutter）、从零新建、以 HideFate 为宿主。**选第三个。**

代码量对比（2026-07 实测）：

| | HideFate | 八紫 BaziWei |
|---|---|---|
| 领域核心逻辑 | **10,824 行**（含 2,322 行测试） | 2,671 行（含测试 374） |
| core-fengshui | 3,406 | 无 |
| core-synthesis | 5,762 | 无 |
| 奇门 | vendor 原样收录 ＋ 同步脚本 | 无 |
| 紫微 | 无 | 147 行（真正干活的是 `dart_iztro` 包） |
| 前端 | 6,955 行 Next PWA（已移动优先） | 3,451 行 Flutter |

三条硬理由：

1. **反向移植会毁掉奇门引擎。** 现在是逐字节 vendored、禁止就地修改、有 24 山全量对拍。
   重写成 Dart 等于重新实现一个奇门引擎，旬首／值符值使／阴阳遁／超接置闰任一处出错都很安静。
2. **不对称是十倍级的。** 往这边搬只需要紫微（而紫微是装个 npm 包）；
   往那边搬要迁 9,168 行手写术数 ＋ 1,935 行测试。
3. **对轨回路要用的机器已经在这边。** `predict.ts` 的 `breakdown` 逐条归因、
   `timeline.ts` 的逐年重算、`simulate.ts` 的反事实推演，正是 §5 三步要用的东西。

**代价（照实记录）**：八紫的 3,451 行 Flutter UI 作废。缓解是八紫本就定位 PWA
（`pubspec.yaml` 写明），且本仓库已有移动端组件基础。

八紫仓库转为只读参考，不再开发。

## 4. 象意字典 —— 本轮最核心的新数据结构

### 4.1 要解决的问题

七杀在疾厄，古法给的是一串候选象：开刀、竞争、官非、性格刚烈、军警武职。
**经典没错，但对具体这个人只有其中一两条会显化。** 用户填入真实经历，
不是给系统打分，是告诉系统「我这颗七杀走的是哪一条道」。

这与统计意义上的概率校准是两回事，且**这个是主线**。

### 4.2 Schema（拟置于 `packages/core-xiangyi/`）

```ts
/** 象源：任何一个可以取象的盘面元素。 */
export type XiangSource =
  | { layer: '命'; system: '八字'; kind: '十神' | '神煞' | '五行' | '刑冲合害'; token: string }
  | { layer: '命'; system: '紫微'; kind: '主星' | '四化' | '格局' | '宫位'; token: string }
  | { layer: '运'; system: '奇门'; kind: '八门' | '九星' | '八神' | '天干' | '格局'; token: string }
  | { layer: '运'; system: '流年'; kind: '干支' | '十神'; token: string }
  | { layer: '风水'; system: '飞星' | '八宅'; kind: '单星' | '组合' | '游年'; token: string };

export interface XiangYi {
  /** 稳定 id，账本与后验都引用它，一经发布不得改写。 */
  readonly id: string;
  readonly source: XiangSource;
  /** 复用 core-synthesis 的 RiskDomain。 */
  readonly domain: RiskDomain;
  readonly valence: '吉' | '凶' | '中';
  /** 显化面：人物象／事件象／物象／身体部位。 */
  readonly facet: '人' | '事' | '物' | '体';
  /** 具体表述，如「开刀、外伤、金属器械所伤」。 */
  readonly statement: string;
  /** 触发条件：需哪些元素同时在场才进入候选。 */
  readonly requires?: readonly XiangCondition[];
  /** 需几层共振才够格进入预测。设 2 以上可挡掉大量单层臆断。 */
  readonly minResonance: 1 | 2 | 3;
  /** 古法先验权重 0–1。**此值不参与学习。** */
  readonly prior: number;
  /** 古法出处，对应 Finding.classic。 */
  readonly classic: string;
  /** 这条象若成真，能不能被干预、被什么干预。见 §8。 */
  readonly interventionability: '空间可调' | '择时可避' | '行为可调' | '不可调';
}

/** 个人后验 —— 唯一随用户数据变化的东西。 */
export interface XiangPosterior {
  readonly personId: string;
  readonly xiangId: string;
  readonly hits: number;      // 明确显化
  readonly partial: number;   // 部分应验
  readonly misses: number;    // 明确「该期此域平安无事」——必须是用户主动填的
  /** Beta 后验均值，向 prior 收缩；样本少时几乎等于 prior。 */
  readonly weight: number;
  readonly evidenceIds: readonly string[];  // 指向预测账本
  readonly updatedAt: string;
}
```

`misses` 必须来自用户**主动**填写的「这年这方面无事」。只记发生过的事，
证据只增不减，象意永远收敛不下去 —— 这是幸存者偏差，UI 必须提供负样本入口。

### 4.3 示例：七杀（八字十神）

| id | facet | domain | statement | minResonance | 可干预性 |
|---|---|---|---|---|---|
| `bazi.qisha.career.compete` | 事 | 事业 | 竞争、创业、独当一面承压 | 1 | 行为可调 |
| `bazi.qisha.legal.lawsuit` | 事 | 官非 | 诉讼、纠纷、被追责 | 2 | 择时可避 |
| `bazi.qisha.health.surgery` | 体 | 健康 | 开刀、外伤、金属器械所伤 | 2 | 空间可调 |
| `bazi.qisha.person.martial` | 人 | 事业 | 军警武职、技术专业、纪律性行业 | 1 | 不可调 |
| `bazi.qisha.mind.decisive` | 人 | 心性 | 刚烈决断、不受约束 | 1 | 不可调 |

同一颗七杀，五条候选。**对轨前五条并列，对轨后剩一到两条。**

### 4.4 三层共振示例

某人某年同时出现：

- **命层**：`bazi.qisha.health.surgery`（大运七杀透干）
- **运层**：奇门占局伤门／死门临值使宫
- **风水层**：当年所居之宅，二黑飞临其主卧所在宫

三层同指健康-金伤，`minResonance: 2` 满足且超额 → 该条预测置信度显著高于任一单层。
若用户后来确认「那年确实动了手术」，则：

1. `bazi.qisha.health.surgery` 的 `hits` +1，其余四条七杀候选**不加分也不减分**
   （未发生 ≠ 反证，除非用户明确填了「那几年事业、官非方面无事」）
2. 系统可信度矩阵（§7 学习对象 B）中「命层 × 健康」「风水层 × 健康」各得一分证据
3. 未来同类共振出现时，该条的权重更高，叙述更具体

这个收敛过程**必须对用户可见**。它比任何一段 AI 生成的文字更能建立信心。

## 5. 对轨回路的执行顺序（顺序不可颠倒）

```
1. 只输入生辰性别
2. 立刻生成一生轨迹：按大运／大限分段，每段 3–5 条可判定的回溯描述
   → 写入账本、盖时间戳、锁死          ← 关键：必须在用户填历史之前
3. 用户逐条对轨：中／部分中／未发生／反向，并可填「该期此域无事」
4. 象意收敛 ＋ 系统可信度更新，当场可见
5. 重算现在与未来，标注置信度来源与哪几层在说话
6. 风水／化解入口此时才出现，且只对「空间可调」的预测出现
```

**第 2 步先于第 3 步是硬性的。** 顺序反了就是冷读，产品价值归零，用户自己也会怀疑。

## 6. 预测账本与居住史

### 6.1 预测账本（append-only）

```ts
export interface PredictionRecord {
  readonly id: string;
  readonly personId: string;
  /** 生成时刻，写入即锁。 */
  readonly createdAt: string;
  /** 各 core 包版本 ＋ 规则集哈希。缺此项则③比对的是两个不同模型。 */
  readonly engineVersion: string;
  /** 生辰 ＋ 居住史 ＋ 化解史的哈希，用于确定性重放。 */
  readonly inputHash: string;
  readonly window: { readonly fromYear: number; readonly toYear: number };
  readonly domain: RiskDomain;
  readonly statement: string;
  readonly candidateXiangIds: readonly string[];
  readonly layers: readonly ('命' | '运' | '风水')[];
  readonly probability: number;
  /** 人群基准率。无可靠基准时置 null 并在 UI 标注「无基准」。 */
  readonly baseRate: number | null;
  /** 事前定义的判定标准 —— 无此项者拒绝写入。 */
  readonly resolution: { readonly criterion: string; readonly judge: '用户自评' | '客观记录' };
  readonly interventionability: XiangYi['interventionability'];
  /** 窗口内是否施做过化解；true 者不参与校准（混杂）。 */
  readonly intervened: boolean;
  readonly status: '待结算' | '已结算' | '窗口过期' | '资料不足';
  readonly outcome?: {
    readonly verdict: '中' | '部分中' | '未发生' | '反向';
    readonly note?: string;
    readonly recordedAt: string;
  };
}

/** 负样本 —— 与 PredictionRecord 同等重要。 */
export interface QuietRecord {
  readonly personId: string;
  readonly year: number;
  readonly domain: RiskDomain;
  readonly note?: string;
}
```

三条写入期约束：

- **无 `resolution` 不得写入。**「今年财运有起伏」永远是准的，这种条目一律拒收。
- **`engineVersion` 与 `inputHash` 必填**，并有确定性重放测试（同输入同版本 → 同输出）。
- **`baseRate` 为 null 时 UI 必须标注**。若某事本来六成人都会遇上，报 60% 等于零信息。

### 6.2 居住史

现有 `PropertyProfile.moveInYear` 是「一间房子的入住年」，属宅视角。
人生轨迹需要人视角：

```ts
export interface ResidencePeriod {
  readonly id: string;
  readonly personId: string;
  readonly propertyId: string;
  readonly fromYear: number;
  readonly toYear: number | null;   // null = 至今
  readonly role: '居家' | '办公' | '兼';
  /** 老宅资料残缺是常态，比照「残缺八字是一等公民」。 */
  readonly fidelity: '罗盘实测' | '大致朝向' | '仅入住年' | '无资料';
}
```

`fidelity` 决定能算什么：

| fidelity | 能算 | 参与学习 |
|---|---|---|
| 罗盘实测 | 全套飞星 ＋ 宫位 ＋ 房间 | ✅ |
| 大致朝向 | 宅盘 ＋ 宫位吉凶，房间层放弃 | ✅（降权） |
| 仅入住年 | 只有元运层与流年紫白 | ❌ |
| 无资料 | 该段风水层置零，明示「此段无风水证据」 | ❌ |

低保真段**不得参与学习**，否则把噪声当断点证据。宁可标「这段看不了」。

### 6.3 断点归因（搬家＝自然实验）

三层在同一年都会说话，事后谁都能认领。只有断点错开时才分得清：

```ts
export type Breakpoint =
  | { readonly year: number; readonly kind: '大运交界' | '大限交界'; readonly personal: true }
  | { readonly year: number; readonly kind: '搬家' | '施做化解'; readonly personal: true }
  | { readonly year: number; readonly kind: '元运换运'; readonly personal: false };
```

- 转折卡在**搬家年**而大运未换 → 风水层对此人此域权重高
- 转折卡在**大运交界**而一直住同一处 → 命层权重高
- 两者都没动、只有流年／奇门在动 → 运层权重高

**`personal: false` 的断点（元运换运 2004／2024）不得用于归因。** 它对全世界同时发生，
没有对照组，与当年任何世界性事件完全纠缠。

### 6.4 风水在系统里有两个角色，数据模型上必须分开

- **证据项**：解释过去为什么这样，参与象意收敛
- **干预项**：改变未来，可选

混在一起会污染回溯 —— 已施化解改写了宅盘，回头算过去时若用改过的盘就算错了。
故居住段之下还要按化解生效日期再切段（`AppliedCure.effectiveFromYear` 已有此概念，
需拉到人生时间轴上）。

## 7. 学习的边界

**可学（两个对象，都可解释、都要给用户看）**

| | 形态 | 数据量要求 |
|---|---|---|
| A. 个人象意后验 | 每条象意一个 Beta 后验，向古法先验收缩 | 几条即开始动 |
| B. 系统 × 领域可信度 | 3 层 × 7 领域 ≈ 21 个数，强先验收缩 | 十几条见效 |

**不可学**

- 飞星权重、十神取象、八宅游年、奇门定局 —— 一律不动
- 任何在 n=1、样本数十的情况下做梯度拟合的做法 —— 只会把噪声学成规律
- 真要动古法权重，须 200+ 条已结算记录，且用分层收缩（每人只学一个偏移量）

**只作后台指标、不进 UI**：Brier Skill Score、可靠性曲线、干预混杂检查。
它们是防止我们自己被自己骗，不是给用户看的。

## 8. 对 README「硬规则」的修订

**规则 4「无化解则不出预测」→ 修订。**

原规则的立意是「只报忧不给解法没有意义」，这在宅盘产品里成立；
但在人生轨迹产品里，它会逼系统为了凑建议而硬编不存在的化解。
有些事本来就不是摆个物件能解决的。

修订后：

> **无化解仍然出预测，但每条预测必须标注可干预性四选一**
> （空间可调／择时可避／行为可调／不可调）。
> 标为「不可调」者，明说风水帮不上，只做预备与提前量；
> 化解 tab 只接收「空间可调」的条目。

影响面：`predict.ts` 顶部策略注释、`Prediction` 类型新增字段、
现有「无化解不出预测」测试需改写为「每条预测必带可干预性标注」。
**这是本轮唯一一处硬规则变更，其余六条不变。**

规则 1（LLM 绝不发明数字）在本轮**加强**：AI 做归因时只能从引擎已算出的
`breakdown` 与收敛后的候选象意里**选**，不得新造理由；
且归因分类必须包含 **「现实层（与盘无关）」** 这一项 ——
一个不能说「这次跟命理风水没关系」的系统，必然退化成确认偏误机器。

### 择时的概念陷阱（P1 已在签名上分开）

「起奇门盘预测」与「择吉时行事」是两件事：

- **占局**：用求测时刻，**不可选**，写入即锁 —— 已实现，`castDivination()` 无时刻参数
- **择吉**：用行动时刻，可选，属规划 —— 尚未实现，将来另立 `Election` 对象

若预测所用的时刻是自己挑的，就是在挑答案，可证伪性当场归零。
复核旧占走 `replayDivination()`：只接受账本里已记录的时刻，且不产生新的占、不写账本、
不参与查重 —— 它存在的唯一目的是让 §5 第 3 步比对的是同一个模型。

### 占局为什么是回路的关键（P1 定案理由）

三层的结算速度差一到两个数量级：

| 层 | 一条预测多久能结算 | 一个用户一年的已结算数据 |
|---|---|---|
| 命层（大运／流年） | 1–10 年 | 约 7 条（七领域各一） |
| 风水层 | 一个居住段（数年） | 更少 |
| **占局** | **天到周** | 理论上无上限 |

象意字典靠证据收敛。只靠命层一年七条，等它收敛要十年，产品活不到那天。
**占局是唯一能让对轨回路在几个月内跑起来的层。**

但两类数据校准的**不是同一个参数，不得混池**：

- 占局对轨 → 校准奇门用神取象 ＋ 系统可信度矩阵（学习对象 B），快
- 命层对轨 → 校准命层象意（学习对象 A），慢

占局数据量会远大于命层，混在一起会把命层信号淹掉。

占局在 §1 的概率结构里担任**触发**项：命层说这个大运有健康风险、
风水层说二黑飞临主卧，两者都不说「哪天」——§4.4 的三层共振只能靠占局落地。

顺带：`feipanPredict.YONG_SHEN_RULES` 那 23 条占类每条都带 `note`（断法纲要），
就是运层象意的原型，P2 的象意字典可直接由此转出，不必手写。

### 一事一占为什么写进签名

允许复占，用户就会同一件事问到满意为止，然后只留下喜欢的那条 ——
对轨数据全废，而且是最难察觉的那种废。故 `castDivination()` **必须**显式接收
当前未结算的占用于查重，首次占传 `[]`：让「我没做查重」成为一个需要主动写下的动作，
而不是忘记调用的默认结果。

查重键由归一化占问 ＋ 占类 ＋ 年命哈希得来，**是启发式**：
挡得住原样再问与改标点，挡不住有心改写措辞。故 UI 还须提供
「这与之前那一占是同一件事」的手动关联，别把查重全押在哈希上。

## 11. P1 落地时定下的三条实现决策

**① 时辰未知走「定盘」，不走降级。**
八字缺时辰仍可得三柱，紫微缺时辰则连命宫都定不了。因此 `castZiWei()` 在缺时辰时
**抛错而非猜一个时辰**，改由 `castZiWeiCandidates()` 排出十三张候选盘（含早子、晚子）
并按命宫地支归组 —— 十三个时辰通常只产生四到六种命宫，对轨时只需分辨这几种。

古法「定盘」本来就是靠反问已发生之事来锁时辰，与 §5 的对轨回路是同一件事。
**这意味着时辰未知的用户不是二等公民，而是第一批产生对轨数据的人。**

**② 立春年界的跨包分歧必须报出来，不得静默。**
上游 iztro 的 `yearDivide: 'exact'` 以**立春当日零时**换年，
core-bazi 的 `liChunOf()` 以**立春时刻**换年。生于「立春当日、立春时刻之前」者，
两者年干支差一位（1990、2000、2024 三年实测均落入此窗口；2013 年窗口仅 13 分钟）。

处理方式：`liChunCaveat()` 检出该窗口并写入 `ZiWeiChart.caveats`，
明说「紫微按 N 年、八字与命卦按 N−1 年，此段请两盘并看」。
**不选边、不静默、不假装一致。**

**③ 上游配置每次调用都显式传入。**
iztro 的 `withOptions({config})` 会写入全局单例（实测调用后 `getConfig()` 已被改写）。
若依赖全局态，同一进程内的调用顺序会改变结果，破坏 §6.1 要求的确定性重放。
故 `PINNED_CONFIG` 每次随调用传入，并有测试锁住「上游全局被污染后本包结果不变」。

### 顺带修掉的一个上游 bug

八紫的 `ziwei_patterns.dart` 中「府相朝垣」写作「天府在财帛且天相在官禄」，
该条件**结构上永不成立** —— 天府系顺行安星，天相恒为天府 +4 宫；
财帛为命宫 +8、官禄为命宫 +4，天府若在财帛，天相必回到命宫。
实测 1152 张盘命中 0 次，对调后命中 97 次。TS 版按古法改为
「天府居官禄、天相居财帛」，并留了可达性回归测试防止被改回去。
这是移植过程中**唯一一处有意偏离上游**。

## 12. P2 落地时定下的四条实现决策

**① 风水层象意不手写，由 core-fengshui 推导生成。**
`STAR_META`（九星脏腑、人物、风险维度）与 `YOU_NIAN_META`（游年八星）已经是单一事实来源，
象意条目从它们推出来即可。同一批断语若在两处各写一份，迟早走样，
而走样的那一处不会有人发现 —— 与「大游年表由翻卦掌推导而非手抄」是同一条理由。
运层同理，由 core-qimen 的 23 条占类**转出**而非重写；
其中 `天气`（外部客观事件）与 `射覆`（测的是术者功力）**有意不转**，
明列在 `skipped` 里而非静默丢弃。

**② 后验用伪计数收缩，不用频率。**
第一条证据就把权重从 0.5 推到 1.0 是这类系统最常见的自欺。
`PRIOR_STRENGTH = 8` 的含义是「要八条证据才能把权重推到先验与实测的中点」。
且成熟度未达门槛时 `learnedShift()` 恒返回 0 —— **不许声称学到了东西**。
排除某条象意的门槛设得更高（须「可参考」且权重跌破先验一半）：
收敛的目标是缩小候选，但缩错了比不缩更糟，被误排除的象意永远没有翻案机会。

**③ 共振门槛由字典自己带，统一执行，且被拦下的要留痕。**
凡涉健康、官非、意外者一律 `minResonance ≥ 2` —— 命层一颗七杀就断人要开刀，
是取象最常见的失控方式，靠门槛挡而不靠自觉。
被拦下的条目进 `rejected` 而非丢弃，`explainRejection()` 要答得出
「命层确有此象，但风水与运层都不支持，未达两层共振」。

**④ 账本守卫全部在写入期执行。**
一条不可证伪的预测一旦进了账本，它污染的是此后所有校准结论，
而且没人会回头查它当初该不该进来。故 `freezePrediction()` 在写入期就拒收：
判据过短或含「有起伏／有好有坏／不太顺」等永真措辞、缺 `engineVersion` 或 `inputHash`、
概率越出 3%–92%、无层、无象意 id、窗口颠倒。
记录返回前 `Object.freeze`，结算产出**新记录**而非改旧的。

配套的两条排除规则同样是硬的：**窗口内施做过化解者不参与校准**
（无法区分「化解生效」与「预测本来就错」），**无基准率者不参与校准**
（不知道人群基线就算不出这条预测提供了多少信息）。
主指标用 Brier Skill Score 而非准确率 —— 报的就是基准率时技巧分为 0，
零信息不该看起来像本事。

**⑤ 居住史的重叠是错、空档只是警告。**
同一角色同一年不可能住两处，必是记错，故判 error；
但人确实可能有几年没记录，空档只判 warning —— 不该因为资料不全就拦着他继续用。
「兼」（住办合一）同时占居家与办公两条轨，与任一角色相撞都算重叠。

**⑥ 风水层按居住段拼接，没记录的年份置零，不用最近一段顶替。**
这是人视角与宅视角最实质的差别。`LifeTimeline.coverage` 会照实报出
「31 年中 12 年可作证据、9 年无记录、10 年资料不足」，并说明补什么资料能换来什么 ——
让人知道补上老宅的大致朝向能换来什么，比默默降级有用得多。

**⑦ 断点归因只在断点单一时才下结论。**
命层与风水层的断点撞在同一年就是混杂，判「无法分辨」且 `usable: false`；
硬判出来的可信度矩阵比没有还糟。
元运换运（2004、2024）标 `personal: false`，单独出现时拒绝归因 ——
它对全世界同时发生，当年的世界性事件与它完全纠缠。
但它**不会污染**同年本来干净的搬家实验，这一点有测试锁住。

`naturalExperiments()` 列出区间内断点单一的年份，供 UI 提示
「这几年最值得回忆一下发生过什么」—— 用户的回忆精力有限，
该花在最有分辨力的年份上，而不是平均摊在四十年里。

### 尚未做的

紫微大限交界年目前由调用方传入（`daXianBoundaryYears`），core-synthesis 刻意不依赖 core-ziwei ——
紫微缺时辰时本就只有候选盘而无定论，硬依赖会把这个不确定性塞进时间轴。

但权重矩阵本身尚未建立，留待 P3 对轨 UI 产出真实数据后再做。

## 13. P3 落地时抓到的三个问题

三个都是实跑界面才暴露的，写在这里以免重犯。

**① 断语与领域对不上（已修）。**
`fromFengShui` 早先按 `riskDomains` 逐维度出条却共用同一句 `whenDeclining`，
于是二黑的「感情」条目写着「久病缠身、寡妇当家、腹疾」。
用户根本无从判定，评出来的证据还会污染那条象意的后验。
根因是 `STAR_META.whenDeclining` 本身是一句复合断语 —— 我们手上没有分维度的文字，
就不该假装有。现改为**每颗星只出一条**，域取首要风险维度，措辞明说是复合应事。
真正的解法是把 STAR_META 的断语按维度拆开，那是 core-fengshui 的事。
已加通用回归锁：**同一句断语不得挂在两个不同领域下**（对旧实现实测能抓出 6 处）。

**② 同一条象意被问四遍 = 证据被放大四倍（已修）。**
紫微本命主星贯穿一生，每个大运段都在场。不去重的话，四条一模一样的记录结算后
会给同一个 xiangId 记上四条证据 —— 而它们其实只是**一个信号**。
现改为全局去重，每条象意只问一次，归属到最早可观察的那一段。

**③ 界面自相矛盾：写着「尚未偏移」却显示动过的数字（已修）。**
成熟度未起步时 `learnedShift()` 返回 0 是对的，但进度条画的是真实后验（60% → 64%）。
说一套显示一套，正是这类界面最容易骗到人的地方。
现改为未起步时**显示先验**，并标注「证据不足（1/3），仍按先验显示」。

顺带：负样本按钮起初做成一行 22px 的小字，违反 README 的 40px 触控标准 ——
而按本项目自己的设计，它跟四个结论按钮同等重要。已改为 44px 虚线框。

## 14. 隐私（本轮升级）

预测账本装的是健康、婚姻、财务的真实经历，比宅盘敏感得多。
README 的本地优先与显式同意策略原样继承，并追加：

- AI 调用前对账本条目做字段脱敏（去除姓名、具体机构、精确日期）
- 账本导出为独立文件，与宅盘导出分开，避免误分享
- 健康类预测继续走现有策略（概率上限 92%、措辞落到「留意与检查」），
  绝不出现诊断性表述
