# 藏聚 HideFate

> 把每一处房产当作**会随年份变化的活系统**：玄空飞星 + 八宅派 + 山向奇门三派合参，
> 结合家人八字，给出带概率、带古法依据、带化解方案的逐年推演。

简体中文优先。全部推算离线完成，资料默认留在本机。

> **正在进行的方向变化**：本项目正从「给一处房产做三派合参」扩展为
> 「以一命二运三风水的顺序推演一生轨迹，并用用户真实经历反向收敛取象范围」。
> 设计决策、象意字典结构、预测账本与分期见 [`docs/ROADMAP.md`](docs/ROADMAP.md)。

### 在手机上试用 PWA

**要点：Service Worker 与「添加到主屏幕」只在安全上下文下可用** ——
即 `https://` 或 `localhost`。这意味着：

| 方式 | 能打开 | SW / 离线 | 可安装到主屏 |
|---|---|---|---|
| 电脑 `npm run dev` → localhost | ✅ | ❌（dev 模式刻意不注册 SW） | ❌ |
| 电脑 `npm run build && npm start` → localhost | ✅ | ✅ | ✅ |
| 手机连同一 WiFi 开 `http://<电脑IP>:3000` | ✅ | ❌ | ❌ |
| 部署到 Vercel / Cloudflare 等（https） | ✅ | ✅ | ✅ |

所以想在手机上完整体验 PWA（装到主屏、断网可用），需要 HTTPS。

#### 推荐：GitHub Pages（不依赖任何第三方服务）

仓库已带好 `.github/workflows/pages.yml`，推送到 `main` 就会自动构建静态版并发布。
只需一次性设置：

1. **仓库必须是 Public** —— GitHub 免费账号只能从公开仓库发布 Pages
   （私有仓库发布 Pages 需要 GitHub Pro）。
2. 仓库 **Settings → Pages → Build and deployment → Source** 选 **GitHub Actions**。
3. 等 Actions 跑完，站点在 `https://<用户名>.github.io/<仓库名>/`。
4. 手机浏览器打开该地址 → 分享 →「添加到主屏幕」。装好后断网也能用。

静态版与本机版的**唯一差别**：Pages 没有服务器，`/api/ai/*` 转发路由不存在，
因此 AI 只能由浏览器直连供应商。这意味着只有对浏览器开放 CORS 的供应商可用
（OpenRouter / Groq / Gemini 已确认可直连；DeepSeek、硅基流动不确定）。
设置页会直接标出当前所选供应商属于哪一类。其余全部功能 —— 三派排盘、预测、
模拟、时间轴、报告 —— 都不受影响，因为它们本来就在本机算。

本机自测静态版（模拟 Pages 的子路径）——与 CI 跑的是同一条命令，无需删任何文件：

```bash
STATIC_EXPORT=1 NEXT_PUBLIC_BASE_PATH=/hidefate NEXT_PUBLIC_AI_DIRECT_ONLY=1 npm run build --workspace=@hidefate/web
```

产物在 `apps/web/out/`，用任意静态服务器挂到 `/hidefate/` 下即可。

#### 其它方式

- **不想公开仓库**：Cloudflare Pages / Netlify 都能从私有仓库免费部署静态站，
  构建命令与上面的环境变量相同（`NEXT_PUBLIC_BASE_PATH` 留空即可）。
- **临时内网穿透**：`npm run build && npm start`（在 `apps/web` 下），
  再跑 `npx cloudflared tunnel --url http://localhost:3000`，用它给的 https 地址打开。
  这条路保留了 `/api/ai/*` 转发，AI 不受 CORS 限制。
- **仅在电脑上看看**：`npm run build --workspace=@hidefate/web` 后
  `npm start --workspace=@hidefate/web`，浏览器开 localhost:3000 切到手机尺寸
  （SW 与安装提示都正常）。

图标已备齐 SVG + 192／512 PNG，Android 与 iOS 装到主屏都会显示「藏」字图标。

## 一命二运三风水：三层怎么分工

| 序 | 层 | 承担什么 | 时间性质 | 包 |
|---|---|---|---|---|
| 一 | 命 | 先验：一生的底盘与分段 | 平滑分段，断点在大运／大限交界 | `core-bazi` `core-ziwei` |
| 二 | 运 | 触发：某一年、某一刻发生什么 | 逐年逐时，无断点 | `core-qimen`（占局）|
| 三 | 风水 | 调节：同命不同运的那部分差异 | **分段常量**，断点在搬家／换运／施做化解 | `core-fengshui` `core-qimen`（山向）|

```
P(事件) = 先验(命) × 调节(风水) × 触发(运)
                ↓
          个人化校准层          ← 唯一会被用户数据改动的地方
```

**古法权重、飞星取象、十神定义一律不参与学习。** 用户的真实经历只用来做两件事：
收敛象意候选（`core-xiangyi` 的个人后验），以及记录预测究竟准不准（`core-ledger`）。
完整设计见 [`docs/ROADMAP.md`](docs/ROADMAP.md)。

## 设计上的几条硬规则

这些不是「最佳实践」，是这个项目的底线，代码与测试都在守着它们：

1. **确定性优先，LLM 绝不发明数字。**
   所有星位、宫位、组合、概率都由 `packages/core-*` 的纯函数算出。
   模型只被允许把这些结论写成通顺中文 —— 约束写死在 `buildAnswerContext()` 的
   system 提示里，并有测试断言其存在。

2. **每一条结论都必须能回答三个问题**：哪几派支持它、有多确定、依据哪条古法。
   这是 `Finding` 类型的三个必填字段，不是可选的展示项。

3. **概率永远收敛在 3%–92%。**
   风水不是决定论，引擎不输出 0% 或 100%，也不说「必定」。

4. **无化解则不出预测。** 只报忧不给解法没有意义。
   唯一例外是古法红线（主卧见五鬼／六煞／二黑／五黄），此时强制出报并补一条通用化解。
   （**本条将在 P5 修订** —— 人生轨迹层面有些事本就不是摆件能解决的，
   改为「仍出预测但必须标注可干预性」。见 [`docs/ROADMAP.md` §8](docs/ROADMAP.md)。）

5. **残缺八字是一等公民。**
   只知出生年也能得到完整的命卦与八宅方位；缺什么、因此哪些结论不成立，一律明示，
   绝不用缺省值冒充数据。

6. **三条建档路径能力完全相同。**
   没有户型图、人不在现场（纯九宫格），与现场罗盘实测得到同样完整的分析，
   差别只反映在置信度上。

## 移动优先（Mobile-First）

界面基准是「一只手、站在屋子里、可能没信号」，桌面只是把手机版居中显示，
**不另做一套布局**。

- **底部 tab 导航**：首页 / 一生 / 占局 / 风水 / 我的 —— **导航顺序即产品顺序**
  （一命、二运、三风水）。成员与模拟降到二级：它们是配置与深度分析，不是日常入口。
- **大九宫格**：375px 屏上每宫约 110×124px，远超 48px 触控标准
- **分步向导**：建房 5 步、加成员 3 步，一屏一件事，随时可回退
- **相机优先**：户型图直接 `capture="environment"` 调后置摄像头，而非先去翻文件
- **卡片 + 可展开**：先给结论，想深究再展开，不一次堆满
- **滑动对比**：What-If 的前后九宫叠在同一位置，拖分隔线对照同一个宫
- **中文排版**：正文 16px（小于 16px 会触发 iOS 聚焦缩放）、行高 1.8
- **离线**：五个 tab 与奇门引擎全部预缓存，断网照常排盘

已实测（375×812）：全部路由无横向溢出，无小于 40px 的触控目标。

深度分析（时间轴、风险矩阵、融合报告、化解追踪、问答）放在「我的」下的二级页，
避免主导航被塞满。

### 关于 React Native

四个计算核心是纯 TypeScript，可直接移到 Expo。移植时需要另做三件事：
山向奇门的 vendor 引擎是浏览器 UMD 包（需 Hermes 下的 eval + window 垫片）、

不会白写。

## 三个上游引擎的处理方式

### 奇门的两层用法

同一个 vendor 引擎承担两件不同的事，**分属不同的层，不要混**：

| | 定局依据 | 属哪一层 | 回答什么 | 入口 |
|---|---|---|---|---|
| 山向奇门 | 坐山 | 三·风水 | 这个地方如何 | `generateShanXiangChart()` |
| 占局 | 求测时刻 | 二·运 | 此刻这件事如何 | `castDivination()` |

占局默认**飞盘鸣法（括囊）**，其盘面分天／人／地三盘，各带奇仪与暗干支，
人盘走九门循环（第九门黄门随飞，不固定中宫），与转盘的八门＋中宫留空结构不同。
转盘时家的投影层尚未实现，传入即抛错。

**三条纪律写在签名里，不是写在注释里**：

1. **占时不可选** —— `castDivination()` 没有时刻参数，一律取调用瞬间。
   时刻可挑就等于答案可挑。复核旧占走 `replayDivination()`，它只接受账本里的时刻且不产生新占。
2. **判据先于盘面** —— `resolution`（何为应验、谁来判、多长窗口）是必填参数，
   不填排不出盘。「今年财运有起伏」这类不可证伪的占在类型层就写不出来。
3. **复占留档，不许挑答案** —— 同一件事可以反复占（换个时辰本就是另一个局，
   多占几次也有助于校准取象），但每一局都编号入列、都要各自结算。
   要防的是**选择性保留**，不是「再问」这个动作本身。

应期只呈现古法材料（用神宫地盘奇仪主近、地盘暗干支主远、空亡待填实、马星主动），
**不换算成天数** —— 窗口由使用者自己承诺，引擎不发明数字。

### 山向奇门 —— 原样复用，零修改

引擎来自 **[kth2/Qimen-pwa](https://github.com/kth2/Qimen-pwa)**，逐字节收录于
`packages/core-qimen/vendor/`（`engine.bundle.js` → `qimen-engine.js`，`core/shanxiang.js`）。
**该目录禁止就地修改**，一切适配都写在 `src/` 中。理由与细节见
[`packages/core-qimen/vendor/README.md`](packages/core-qimen/vendor/README.md)。

- 定局法：**坐山三元**（`method: 'standard'`），传入未实现的流派会**抛错而非静默出错盘**
- 局表与时家奇门同源，可对拍验证；测试里做了 24 山全量对拍
- 引擎 416 KB，属可选层，**按需懒加载**，不开启就完全不下载
- Service Worker 会预缓存它，断网也能排盘

一个关键不变量由测试强制守住：**上游的二十四山罗盘环与本项目飞星核心是同一个环**
（逐度扫描 360° 比对）。所以「坐山」这一个输入能同时驱动三派，不会出现两套罗盘打架。

### 紫微 —— 回到上游原生

**[iztro](https://github.com/SylarLong/iztro)** 本身就是 TypeScript 包，
而 kth2/bazi-app 用的 `dart_iztro` 是它的 Dart 移植。所以这里不是「把 Dart 翻成 TS」，
是**回到原生**，直接 `npm i iztro`。`packages/core-ziwei` 只做四件事，不碰安星算法：

- **输入归一**：农历 → 公历（与 core-bazi 走同一条转换）、真太阳时、时辰索引
- **配置钉死并逐次显式传入** —— iztro 的 `withOptions({config})` 会写全局单例，
  依赖全局态则同进程内调用顺序会改变结果，破坏账本的确定性重放
- **结果投影**为只读、可序列化的纯数据（供 Dexie 存储与账本哈希）
- **分歧与残缺一律显式报出**

两处必须知道的取舍：

1. **年界与 core-bazi 对齐到立春，但对不齐的那一小段要报出来。**
   iztro 以「立春当日零时」换年，core-bazi 以「立春时刻」换年。
   生于立春当日、立春时刻之前者两边年干支差一位（1990／2000／2024 实测均落此窗口；
   2013 年窗口仅 13 分钟）。这种情况会带一条保留意见明说「紫微按 N 年、八字按 N−1 年，
   两盘并看」——**不选边、不静默、不假装一致**。
2. **时辰未知走定盘，不走降级。** 八字缺时辰仍有三柱，紫微缺时辰连命宫都定不了。
   故 `castZiWei()` 缺时辰直接抛错，改由 `castZiWeiCandidates()` 排十三张候选盘
   （含早子、晚子）按命宫地支归组 —— 通常只剩四到六种命宫。
   古法定盘本就是靠反问已发生之事锁时辰，与对轨回路是同一件事。

格局判定（`patterns.ts`）是本项目自己的一层，iztro 不提供，判据移植自 bazi-app。
**唯一一处有意偏离上游**：府相朝垣的宫位条件在上游写反（天府在财帛则天相必回命宫，
结构上永不触发，1152 张盘实测命中 0 次），已按古法改正并留了可达性回归测试。

### 八字 —— 移植而非引用

**[kth2/bazi-app](https://github.com/kth2/bazi-app)** 是 Dart/Flutter，其计算内核在
pub.dev 的 `bazi_core` 包中，无法直接在 TypeScript 里复用。因此：

- `packages/core-bazi/src/elementStrength.ts` 是该项目
  `lib/core/engine/element_strength.dart` 的**逐项等价移植** ——
  权重（天干 1.0、地支年 1.0／月 1.8／日 1.0／时 1.0）、藏干配比（0.7/0.3、0.6/0.3/0.1）、
  旺相休囚死系数（1.4/1.2/1.0/0.8/0.6）、身强弱阈值（55／42）全部保持一致，
  确保同一个人在两边得到相同的五行结论。
- 天文底座（节气、干支、真太阳时）改用 `lunar-typescript`（与上游 sxwnl 同源算法）。
- 新增了上游不需要处理的**残缺八字分级推算**。

## 门派算法要点

**玄空飞星**：元运数入中排运盘 → 取坐山／向首所在宫之运星分别入中排山盘／向盘 →
阴阳依「该运星本宫中与坐山同元龙之山」而定 → 兼向逾 3° 起替卦（二十四山起星诀）。

五入中无卦无山，借宫规则各家不一，故做成可配置（`CenterFiveRule`），
默认「随运星」，并在推导链中明说用了哪一条。

已用公开盘式校验：八运子山午向＝双星会向、八运乾山巽向／巽山乾向＝旺山旺向。

**八宅**：大游年表**由翻卦掌变爻规则推导生成**，不是手抄表。
这个决定来自实际教训 —— 初版手写表在震、巽、离三宫抄错了五鬼／六煞与绝命／祸害，
是对称性自检测试抓出来的。现在表由 `buildYouNianRow()` 推出，另有四卦公开表作外部锚点。

**房间分「宜吉／宜凶」，不是一视同仁**。这是模型里另一条容易写反的规则：
古法「吉方宜开、凶方宜压」—— 厕所、储藏、楼梯落在凶方是**正解**（以凶制凶），
它们若占了财位或文昌才是败笔。早期版本只按房间权重加权，会把「厕所压绝命方」
判成高风险，与实务完全相反。现由 `ROOM_META.nature` 三分，并统一经
`judgeRoomPlacement()` 出结论 —— 九宫详情与布局体检共用同一判据，
不会出现「一处说压得好、另一处说占了吉方」的自相矛盾。

**布局体检独立于飞星**。除了「星落在哪一宫」，还要看**房间彼此的相对关系**：
穿堂煞（大门与后门一线对穿）、污秽压吉、楼梯或厕所落中宫、神位安置、
灶位与五黄二黑同宫、开门见厕。这些是上门看风水最先指出的东西，
却与任何飞星数字无关，故单列 `layoutRules.ts`。

**五黄与二黑不参与平均**。这条单独说，因为它是实务与代码最容易背离的地方：
若把双星取均值，「五黄配一白」会被算成吉方，与古法完全相反
（《紫白诀》：「五黄正煞，不拘临方到向，人口常损」）。
因此二者比照缺角，另立**独立扣分项**，同宫吉星只能泄化、不能抵销。
`shaPenalty.test.ts` 用行为断言锁住这一点，防止回归。

- 五行力量与参考实现对齐、残缺八字各档位的降级行为
- 奇门 24 山定局与引擎全量对拍、360° 罗盘环跨包一致性
- 紫微公开锚点、十三时辰定盘归组、立春年界跨包分歧必被标注、
  流年干支与八字流年一致、格局十一式各有锚点
- 占局三条纪律的强制力：占时不可指定、判据不合格拒绝起局、窗口内复占被挡；
  九门齐飞互不重复、应期只给古法材料、同时刻重放得同一盘
- 象意字典 id 唯一、健康／官非／意外一律两层门槛、风水层断语随上游知识库自动跟上、
  奇门 23 占类恰好 21 转出 2 跳过、后验向先验收缩且未起步时不许声称学到东西
- 账本四条守卫：不可证伪的措辞写入期被拒、缺引擎版本或输入哈希被拒、
  记录深冻不可就地改、重复结算被拒；干预混杂样本不参与校准、
  报的就是基准率时技巧分为 0
- 居住史重叠是错、空档只是警告；低保真段不作证据；风水层按居住段拼接、
  无记录的年份置零不顶替；元运换运拒绝归因、命层与风水层断点撞车判为混杂
- 同一句断语不得跨领域复用（域名与文字必须对得上）
- 共振按 token 出处算：流年上的七杀说话的是运层，因此三层共振真能达到
- 占局查重键不含占类；复占放行但编号留档，序号计入已结算的旧占
- 事件模板：不得出现任何一层都发不出来的 token、共振门槛不得够不着（可达性锁）
- 事件必须有运层触发；月级事件还要年月并临（两路运层信号）
- 双星组合 53 组（含对称向），事件层用组合而非拆开的单星
- 动气：无动气之宫不发风水 token；应期强度三因子相乘而非取平均
- 白话层：术语解释不得用术语搪塞、无事时不编正能量、同输入同输出可重放
- 组合断语必须自足（不得写「同上」——界面是随机取一条渲染，不是顺序阅读）
- 神煞四式（驿马／桃花／红鸾／天喜）的年支推导与对称性
- 合参的可追溯性（每条断语必带门派与古法依据）
- 概率上下限、无化解不出预测、房间优先级严格排序、感情红线强制触发
- 五黄二黑不可被抵销、流年火生土加重、摘要不把负分之宫吹成吉方

**AI 对话**（已接线）：

在「我的 → AI 设置」填入任一 OpenAI 兼容端点的 Base URL 与 API Key，
点「拉取可用模型列表」即可从 `GET {baseUrl}/models` **实时拉取该 API 当前可用的全部模型**
并从中选用 —— 刻意不内置模型清单，因为供应商随时上下架，写死的列表必然过期。

- 内置预设：DeepSeek、Groq、OpenRouter、Gemini（OpenAI 兼容层）、硅基流动、Ollama（本机）、自定义
- 免费模型会被标出并排在列表前面（依 `pricing` 或 `:free` 后缀判定）
- 请求默认经本机 Next 路由 `/api/ai/*` 转发，以绕开多数供应商未开放的浏览器 CORS；
  可在设置里改为直连。转发层不存储任何东西，Key 与对话都只是过路
- 对话会附上完整盘面（九宫、成员命卦与八字精度、当前模拟状态），
  system 提示明令模型**不得修改任何星位、宫位与概率**，只能引用与解释
- 想让资料一步都不出这台设备，可选 Ollama 在本机跑模型

**未完成 / 已知限制**：

- **户型图只作留存**，尚未实现图上框选房间与自动划分宫位；
  目前三条路径最终都落到同一个九宫映射，故分析能力不受影响。
- **罗盘实测路径**目前是手填度数，未接设备方位传感器。

- 概率模型的各项权重是基于古法轻重的**工程化取值**，非统计拟合。
  它们全部对外暴露在 `Prediction.breakdown` 中，可复算、可调整。
